## 1. Зачем документ

Рефакторинг общей сборки имени файла упёрся в вопрос, на который в коде нет
ответа: **что вообще должно быть в имени и какие сочетания настроек имеют
смысл**. Попытка свести десять точек сборки в одну обнажила, что часть
сочетаний не работает, часть работает не так, как читается, а часть настроек
дублирует друг друга.

Документ фиксирует цели форматов, разрешённые комбинации, найденные дефекты
и принятую схему имён. До него порядок работ был «сначала рефакторинг» —
после него рефакторинг стоит последним, потому что схлопывать имеет смысл
уже правильное поведение.

## 2. Цели форматов

Четыре формата решают четыре разные задачи. Из этого следует, какие режимы
разбивки для каждого осмысленны.

| Формат | Кому и зачем | Как дробится |
|--------|--------------|--------------|
| **DOCX** | человеку: прочитать, отправить, распечатать | по календарю — дни, месяцы, посты |
| **MD** | машине: RAG-корпус, NotebookLM, локальный поиск | по объёму — чанки под контекстное окно |
| **JSON** | машине: структурированный вход для Библиотекаря и скриптов | по объёму |
| **HTML** | человеку: просмотр в браузере, Ctrl+F, дерево тредов | не дробится |

**Матрица режимов после решений этого документа:**

| Режим | DOCX | MD | JSON | HTML |
|-------|:----:|:--:|:----:|:----:|
| единый файл | ✅ | ✅ | ✅ | ✅ |
| по дням | ✅ | ⛔ | ⛔ | ⛔ |
| по месяцам | ✅ | ⛔ | ⛔ | ⛔ |
| по постам | ✅ | ✅ | ✅ | ✅ |
| чанки по словам (`ai_split`) | ⛔ | ✅ | ✅ | ⛔ |

Обоснование запретов, а не «просто не реализовано»:

- **Календарное дробление MD/JSON вредит корпусу.** Чанк, обрезанный по
  полуночи, теряет контекст обсуждения. Для корпуса важен объём, а не дата.
- **Чанки в DOCX не нужны человеку.** Никто не читает «часть 3 из 7» —
  для документа осмысленна календарная граница, а не граница по словам.
- **Дробление HTML убивает его единственное преимущество** — поиск по
  всему архиву в одном файле. См. открытый вопрос O-1.

## 3. Допустимые комбинации по типам чата

| Настройка | Канал | Группа | Форум | Личка |
|-----------|:-----:|:------:|:-----:|:-----:|
| единый / по дням / по месяцам | ✅ | ✅ | ✅ по топику | ✅ |
| **по постам** | ✅ | ⛔ блокировать | ⛔ блокировать | ⛔ блокировать |
| комментарии | ✅ | ⛔ их не бывает | ⛔ | ⛔ |
| фильтр участников | ✅ = комментаторы | ✅ | ✅ | ⚠️ выбор из двоих |
| ветки (сообщения + ответы) | ⚠️ только по комментариям | ✅ | ✅ | ⚠️ смысла мало |
| выбор топика | ⛔ | ⛔ | ✅ | ⛔ |

⛔ — выключать элемент в UI. ⚠️ — работает, но требует подсказки словами.

**Порог по числу файлов.** Даже в канале «по постам» может дать тысячи
файлов. В окне «Проверьте перед стартом» — строка «будет создано ~N файлов»
с акцентом при N > 100, независимо от типа чата.

## 4. Найденные дефекты

### D-1. Утечка скрытых комментариев в DOCX «по постам» 🔴

`DocxGenerator._generate_by_posts()` берёт комментарии **вторым запросом**,
`get_post_with_comments(chat_id, post_id)`, и эти строки не проходят через
`_apply_user_filter()`. В режиме «кроме выбранных» текст, медиа и расшифровки
исключённого участника попадают в документ целиком — при том что имя файла
обещает обратное.

Воспроизведение на чистом `main` (630fd3c):

```
Канал_except_Мария_comments_post_100_fullchat.docx
  текст Марии в документе: ДА — УТЕЧКА
```

Три остальных формата чисты — у них комментарии берутся из того же
отфильтрованного набора строк:

```
MarkdownGenerator    заглушка ок
JsonGenerator        заглушка ок
HtmlGenerator        заглушка ок
```

Это тот самый класс дыр, который закрывал FEAT-6, и он живёт в релизе v1.7.3.

### D-2. Фильтр в режиме «по постам» вымывает сами посты 🔴

`get_messages(user_ids=...)` фильтрует весь набор строк разом, не различая
пост и комментарий. В канале посты идут от самого канала (Variant A-2),
комментарии — от людей. Отсюда:

| Выбран | «только выбранные» | «кроме выбранных» |
|--------|--------------------|-------------------|
| Мария (комментатор) | постов не остаётся → `EmptyDataError` | все посты, реплики Марии заглушками ✅ |
| канал (автор постов) | все посты, ноль комментариев | посты заглушками, комментарии целы |

Осмысленно ровно одно сочетание из четырёх. Режима «посты от Марии»
не существует в природе — посты бывают только от автора канала.

### D-3. Пропуск фрагмента фильтра в именах «по постам» (I11) ✅ закрыт

`generate_by_posts()` в JSON/MD/HTML не включает в имя ни фрагмент фильтра,
ни имя участника. Выгрузка с фильтром и полный архив тех же постов за тот же
период получают побайтово одинаковые имена, вторая молча затирает первую.
DOCX не страдал — он собирал имя через `_build_path()`.

**Закрыт (сентябрь 2026):** все десять точек сборки разведены на общую
`_build_base_name()`, фильтр в имя кладёт она, а не каждый путь по-своему.
Охраняется `tests/test_features/test_export_naming.py` — проверено мутацией:
выброшенный фрагмент фильтра роняет 24 теста.

### D-4. Блокировка «по постам» для не-каналов (I3) не реализована 🔴

В `PROJECT_ANALYSIS.md` I3 числится исправленным. В коде защиты нет нигде:

- живая панель настроек — `SettingsPanel` в `ui/main_window.py:322`,
  `self._split_post` не выключается никогда;
- вторая панель, `features/parser/ui.py`, к экспорту не подключена (ARCH-1),
  и даже там обработчик `_on_split_changed` только показывает строку
  комментариев, а режим не запрещает.

Следствие: в группе у каждого сообщения `is_comment=0`, значит каждое
считается постом. Десять тысяч сообщений — десять тысяч файлов.

### D-5. «По дням» и «по месяцам» молча игнорируются в MD/JSON/HTML 🟡

В `features/export/ui.py` у трёх форматов есть только развилка
`if p.split_mode == "post"`, всё остальное падает в обычный `generate()`.
DOCX + MD с режимом «по дням» даёт девяносто docx и один md, без
предупреждения. Решение — не реализовывать календарное дробление, а сказать
об этом в интерфейсе (см. §2).

### D-6. Мусор и дублирование в именах ✅ закрыт (Р-3…Р-7)

| Что | Почему мусор |
|-----|--------------|
| `archive` в имени DOCX | значение слота `kind` в режиме «единый файл»; одинаково у всех таких выгрузок, не различает ничего; у трёх остальных форматов его нет |
| метка периода рядом с `day_`/`month_` | `Чат_day_2024-01-15_..._2024-01-01_to_2024-03-31.docx` — вторая дата одинакова на всех файлах выгрузки |
| `username` | заполняется **только** когда фильтр в режиме include и отмечен ровно один (`ui/main_window.py:1358`), то есть это тот же фильтр, выраженный вторым способом |
| `fullchat` | это `period_label`, он про время («за всё время», альтернатива `2026-01-01_to_2026-03-31`), а читается как «весь чат» — и с фильтром прямо врёт |

Дублирование `username` — источник D-3. Из-за него в контракте `UserFilter`
появилось правило «include, 1 выбран → пустая строка, имя подставит
существующий `user_part`». В `generate_by_posts()` никакого `user_part` нет,
и правило превратилось в дыру.

## 5. Принятые решения

| # | Решение |
|---|---------|
| **Р-1** | Фильтр в режиме «по постам» применяется **только к комментариям**. Пост печатается всегда целиком, никогда не заменяется заглушкой и не исчезает. |
| **Р-2** | Комментарии в DOCX «по постам» проходят через `_apply_user_filter()`, как и в трёх остальных форматах. Закрывает D-1. |
| **Р-3** ✅ | «Кто» в имени файла собирает **только** `UserFilter`. `username` из именования уходит. `name_part()` теряет случай «include-1 → пустая строка»: один выбранный даёт честное `only_Мария`. |
| **Р-4** ✅ | Слот `kind` (`post_42`, `day_2024-01-15`, `month_2024-01`) переезжает в начало имени, сразу после чата и топика — единым правилом для всех видов, иначе снова получится два порядка. |
| **Р-5** ✅ | `archive` убирается. Единый файл не получает слова в слоте `kind`. |
| **Р-6** ✅ | Метка периода не пишется, если слот `kind` уже несёт дату (`day_`, `month_`). |
| **Р-7** ✅ | `fullchat` → `alltime`. Английское служебное слово по конвенции проекта, однородно с `2026-01-01_to_2026-03-31`, не претендует на полноту содержимого. |
| **Р-8** | Календарное дробление для MD/JSON/HTML не реализуется; `ai_split` не реализуется для DOCX и убирается у HTML. Ограничения проговариваются в UI, а не молчат. |
| **Р-9** | «По постам» блокируется в UI для всех типов чата, кроме broadcast-канала. Плюс страховка в `ExportWorker`: пришёл `split_mode="post"` не для канала → лог и откат на «единый». |

## 6. Схема имён

```
{чат}[_{топик}][_{kind}][_{фильтр}][_comments][_{период}].{ext}
```

| Слот | Когда есть | Примеры |
|------|------------|---------|
| чат | всегда | `Канал`, `Группа` |
| топик | только форум | `Терраса` |
| kind | кроме единого файла | `post_42`, `day_2024-01-15`, `month_2024-01` |
| фильтр | фильтр активен | `only_Мария`, `except_Мария`, `only_3_users_7f2a`, `except_2_users_7f2a` |
| comments | комментарии включены | `comments` |
| период | kind не несёт даты | `alltime`, `2024-01-01_to_2024-03-31` |

Служебные слова английские (`only`, `except`, `post`, `day`, `month`,
`comments`, `threads`, `alltime`, `part`). Имена участников и названия
топиков — данные, остаются как есть.

Четыре символа хеша — `sha256` от набора ID. Обязательны: без них два разных
набора по трое дают одинаковое `only_3_users`, и вторая выгрузка молча
затирает первую.

### Примеры

| Что выгружаем | Имя |
|---------------|-----|
| канал целиком | `Канал_alltime.docx` |
| канал за квартал | `Канал_2024-01-01_to_2024-03-31.docx` |
| пост с обсуждением | `Канал_post_42_comments_alltime.md` |
| пост, только комментарии Марии | `Канал_post_42_only_Мария_comments_alltime.md` |
| пост, кроме Марии | `Канал_post_42_except_Мария_comments_alltime.md` |
| группа по дням | `Группа_day_2024-01-15.docx` |
| группа по месяцам | `Группа_month_2024-01.docx` |
| форум, топик «Терраса» | `Группа_Терраса_alltime.docx` |
| ветки Марии | `Группа_only_Мария_threads_alltime.docx` |
| кроме троих | `Группа_except_3_users_7f2a_alltime.docx` |
| чанки для RAG | `Группа_alltime_part_1.md` |

## 7. Границы с Библиотекарем

Логика фильтра дублироваться не должна: `features/export/filters.py` уже без
Qt и без Telethon — именно это делает его пригодным для импорта откуда
угодно. Дублироваться будет интерфейс выбора участников, а не контракт.

Важнее другое — **фильтр по автору для Библиотекаря это фасет запроса**,
а не свойство файлов. «Покажи, что писала Мария» задаётся в момент вопроса
и меняется каждый раз. Отфильтровав при выгрузке, решение запекают в корпус
навсегда: чтобы спросить про другого человека, придётся перевыгружать.

Отсюда развилка целей, которую стоит зафиксировать до того, как Библиотекарь
написан:

| Назначение фильтра | Форматы | Смысл | Заглушки |
|--------------------|---------|-------|----------|
| **для документа** | DOCX, HTML | отдать человеку файл, где чужих слов нет | нужны — иначе рвётся контекст ответов |
| **для корпуса** | MD, JSON | почти всегда не нужен: Библиотекарь отфильтрует на запросе | вредны — индекс наполняется строками «🚫 Сообщение скрыто» |

`_hide_row()` — понятие документа. Для поискового индекса оно бессмысленно
и переносить его в Библиотекаря не надо.

JSON пишет `sender_id` и `username` в каждой записи, поэтому естественный
вход Библиотекаря — JSON.

## 8. Открытые вопросы

**O-1. Дробление HTML по размеру.** Чанки под контекстное окно нейросети
HTML не нужны — решено. Но у HTML есть свой, другой повод дробиться:
архив на сто тысяч сообщений подвешивает браузер. Это дробление по весу
страницы, а не по словам, и порог у него другой. Нужно ли — не решено.

**O-2. `user_filter_mode="threads"` отдельно от `UserFilter`.** Два механизма
описывают одно и то же: ветки требуют ровно одного участника в режиме
include. Просится флагом внутрь фильтра, но это отдельная задача со своим
объёмом.

**O-3. Добивка нулями номера поста.** При номере поста в начале имени
сортировка станет текстовой: `post_1, post_10, post_100, post_2`. Лечится
добивкой (`post_0042`), но тогда номер в имени перестаёт совпадать с номером
в ссылке `t.me/c/…/42`. Не решено.

**O-4. Судьба параметра `username` в сигнатурах.** ✅ Решено: оставлен
принимаемым, но на имя файла не влияет. Удаление тронуло бы четыре
`generate()`, четыре `_generate_threads()`, `ExportParams` и `main_window` —
это отдельная правка, и делать её в одном заходе со сменой схемы имён
значило бы смешать два разных повода для регрессии.

Внутри `_generate_threads()` `username` по-прежнему нужен и работает: там
участник приходит отдельным `user_id`, а не фильтром (O-2), и попадает в
имя через слот `who` — иначе ветки всех участников чата получили бы одно
имя. Слот уступает фильтру, когда тот своё «кто» уже назвал.
